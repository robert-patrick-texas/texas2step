# Development

This guide is for working on texas2step itself: running it from source, testing,
building the documentation site and the Debian package, and making a release. To
install texas2step on a server, see [Install](install.md).

## Prerequisites

* Python 3.11 or newer, and [uv](https://docs.astral.sh/uv/).
* Node.js 20 or newer (24 LTS recommended), only to change the web UI.
* [Go](https://go.dev/dl/) at the version `t2s/go.mod` names or newer, for [t2s](#t2s):
  `make check` tests it, and a release builds it.
* For the `.deb`: an Ubuntu 26.04 amd64 host with `dpkg-deb`, `binutils` and,
  optionally, `lintian`.

## Run from source

```bash
git clone https://github.com/robert-patrick-texas/texas2step.git
cd texas2step
uv sync          # creates .venv with the app plus the dev and docs tools
make dev         # http://127.0.0.1:8080
```

The built UI is committed under `src/texas2step/static/`, so the server runs without
Node. `make dev` keeps saved results in `texas2step.db` and the active clients in
`texas2step-clients.db`, both in the working folder; `TEXAS2STEP_CLIENTS_FILE=texas2step-clients.db
uv run texas2step clients` lists them. To work on the UI, run `make web-watch` in a second terminal. It rebuilds the
bundle on every change, unminified and with source maps.

To try the server under a path prefix the way nginx publishes it, send the header
nginx would:

```bash
curl -s -H 'X-Forwarded-Prefix: /texas2step' http://127.0.0.1:8080/ | grep '<base'
# <base href="/texas2step/" />
```

## Make targets

| Target | What it does |
|---|---|
| `make dev` | Run the server on 127.0.0.1:8080 |
| `make web` | Install Node dependencies, typecheck and bundle the UI into `src/texas2step/static` |
| `make web-watch` | Rebuild the UI on change |
| `make test` | pytest, including WebRTC round trips on loopback |
| `make lint` / `make fmt` | ruff and tsc / ruff format and autofix |
| `make check` | lint and test, and t2s's tests |
| `make docs` | Render every `.md` file into the static site in `html/` |
| `make docs-watch` | Re-render `html/` whenever a `.md` file changes |
| `make sheet` | Print the one-page sheet, `docs/at-a-glance.pdf` (US Letter) and `docs/at-a-glance-a4.pdf` (A4), from `scripts/at-a-glance.html` |
| `make deb` | Build `dist/texas2step-<version>-1-amd64.deb` and `dist/texas2step-setup` |
| `make version` | Print the version |
| `make upgrade` | Move every Python, npm and Go dependency to its newest release, then rebuild the UI |
| `make t2s` | Build t2s for Linux, macOS and Windows (amd64, arm64) into `dist/` |
| `make t2s-test` | gofmt, go vet (for Linux, macOS and Windows) and go test for t2s |

## Project layout

```text
src/texas2step/        Python package
  app.py               FastAPI app factory, path-prefix support, static UI, SPA routes
  api/wire.py          measurement primitives: ping, down, up, ws, rtc/offer
  api/meta.py          info, whoami, locations, health
  api/measure.py       server-side measurement functions
  api/results.py       result history
  engine.py            Python measurement engine (CLI + /measure)
  rtc.py               WebRTC data-channel echo (aiortc), UDP port range
  page.py              HTML shell: path prefix, version, default theme, branding
  config_template.toml the settings file the package installs, every setting documented
  config_merge.py      `texas2step config merge`: carries settings into a new template
  config_edit.py       `texas2step config set` / `add-location`: edits in place
  update.py            `texas2step update`: fetch a release, run its setup tool, install
  stats.py             shared statistical definitions
  store.py             SQLite result store
  static/              built web UI (generated by web/build.mjs; committed)
web/                   TypeScript client (no runtime dependencies)
  src/engine/          browser measurement engine
  src/ui/              gauge, link animation, charts, views
t2s/                   t2s, the command-line client, in Go (docs/t2s.md)
  internal/stats/      the statistics, as stats.py
  internal/quality/    call quality and responsiveness, as quality.py
  internal/engine/     latency, transfers, the UDP probe (pion WebRTC), a full test
  internal/monitor/    Monitor: probing, outages, call slices, the panel
  internal/diag/       Diag: every row, NAT and egress, the table
  internal/update/     t2s update
tests/                 pytest: stats, config, API, store, WebRTC, end-to-end
docs/                  the documentation, in Markdown
scripts/build_docs.py  Markdown → html/ (the GitHub Pages site)
deploy/                files the package installs: systemd units, defaults, nginx snippets
packaging/             Debian packaging: build-deb.sh, control, maintainer scripts,
                       and texas2step-setup.py, the operators' check-and-install tool
.github/workflows/     GitHub Pages publishing
legacy/                the original single-file prototype, kept for reference
```

## Code conventions

* Server-side code is Python. Browser code is TypeScript, bundled by esbuild with no
  runtime dependencies and no CDN, so the page works on networks without internet
  access.
* Statistical definitions live in `stats.py` and `web/src/engine/stats.ts` and must
  stay in step. [Methodology](methodology.md) documents them. t2s has them a third time,
  in Go; `tests/methodology-cases.json` holds the Python engine's answers to a set of
  inputs, which pytest and t2s's tests both check (see [t2s](#t2s)).
* After changing anything under `web/`, run `make web` and commit the regenerated
  `src/texas2step/static/` along with the source.
* The one piece of browser code that isn't ours is Swagger UI, the OpenAPI explorer at
  `/api/docs`. `web/build.mjs` copies it, with its license files, from the pinned
  `swagger-ui-dist` npm package into `static/assets/swagger/`, so the explorer needs no
  CDN. That package depends on `@scarf/scarf`, an install-time analytics reporter; its
  install script is denied in `web/package.json` (`allowScripts`), so it never runs.
* Dependencies are pinned exactly (`uv.lock`, `web/package.json` and
  `web/package-lock.json`), so builds are repeatable. `make upgrade` moves them all to
  their newest releases.

## Tests

`make test` runs the whole suite in about 15 seconds:

* Unit tests: statistics, settings, the result store.
* API tests: a FastAPI test client, including the path-prefix handling.
* End-to-end tests against a real uvicorn server on loopback: HTTP latency,
  multi-stream throughput, and WebRTC packet loss, including the pinned UDP port range.
* t2s against the same server (`tests/test_t2s.py`, skipped without Go): its result has
  the Python engine's keys in the same order, a saved one is in History, and Monitor and
  Diag answer.

The WebRTC tests need a non-loopback address on the host, because WebRTC never offers
127.0.0.1 as a candidate.

## t2s

t2s, the command-line client ([t2s](t2s.md)), is a Go module in `t2s/`. It measures by
the methodology of `engine.py` and `quality.py`, and writes the result format they write.
Its version is the project's: `make t2s` stamps `make version` into each build
(`-X main.version=`), so `__init__.py` stays the one place it is written; a plain
`go build` says `dev`.

* `make t2s` builds every platform's file into `dist/` with no cgo and `-trimpath`:
  `t2s-linux-amd64`, `t2s-linux-arm64`, `t2s-macos-amd64`, `t2s-macos-arm64`,
  `t2s-windows-amd64.exe` and `t2s-windows-arm64.exe`. They are fully static, but for
  macOS's, which link only the system library every Mac has, as every Mac program must;
  Go's linker signs the Apple silicon one ad hoc, as macOS requires there, even from
  Linux. Go calls macOS `darwin`; the files say `macos`. The names carry no version, so
  `releases/latest/download/<name>` always gives the newest, and `t2s update` finds its
  own by name.
* `make t2s-test` runs gofmt, go vet (for Linux, and for macOS's and Windows' own files)
  and go test. The t2s workflow runs the tests on Linux, macOS and Windows.
* `tests/methodology-cases.json` is the Python engine's answers to a set of inputs:
  percentiles, summaries, throughput, the loss summary, one-way delays, call quality,
  responsiveness and bufferbloat. t2s's tests check its own answers against them, and
  `tests/test_methodology_cases.py` checks the file still says what the Python code does.
  After changing the methodology, write it again and run both:

  ```bash
  uv run python scripts/methodology_cases.py && make test t2s-test
  ```

* `.github/workflows/t2s.yml` runs t2s's tests on Linux and on Windows, builds every
  platform's file, and runs `tests/test_t2s.py`, on each push that changes t2s.

## Documentation site

`scripts/build_docs.py` turns every `.md` file in the repository into a static site in
`html/`:

* `README.md` becomes the index page, and every page has a sidebar that links to all
  the others.
* Links between `.md` files become links between pages.
* A broken link or anchor fails the build.

`html/` isn't committed. On this development server it is served for review by nginx at
`/texas2step/`, through the symlink `/var/www/html/texas2step → html/`. Run `make docs`,
or keep `make docs-watch` running while you edit.

On GitHub, `.github/workflows/docs.yml` builds the same site and publishes it to GitHub
Pages on every push to `main` that touches Markdown. It needs Pages enabled once: in the
repository settings, **Pages → Source: GitHub Actions**. Until then the workflow builds
the site and skips the deploy with a notice.

The site, the screenshots in `docs/images/` and the printed sheet below wear the Energy
theme: its blue gradient in `scripts/docs.css`, and the app's own tab icon, the white star
on blue in `web/public/favicon.svg`, as the logo. Take new screenshots in that theme, at
1366 pixels wide.

Every PDF under `docs/` is published with the site. Two are the
[at-a-glance](at-a-glance.md) page condensed onto one page to print: `docs/at-a-glance.pdf`
on US Letter and `docs/at-a-glance-a4.pdf` on A4. Their source is
`scripts/at-a-glance.html`, so change it along with the page, then run `make sheet` and
commit both PDFs. `make sheet` prints with Playwright's Chromium, installed once with
`uv run --with playwright playwright install chromium`, and fails, writing neither, if the
sheet runs over one page on either paper. It wants two fonts installed: JetBrains Mono (`fonts-jetbrains-mono`) and
Inter's TrueType files, from `extras/ttf/` in an [Inter release](https://github.com/rsms/inter/releases).
Chromium embeds the OpenType build of Inter that Ubuntu's `fonts-inter` installs as Type 3
fonts, whose text loses spaces when copied; `make sheet` warns when that happens.

## Build the Debian package

```bash
make deb          # or: packaging/build-deb.sh
```

`packaging/build-deb.sh`:

* Builds the wheel.
* Creates a relocatable virtualenv on the system `/usr/bin/python3`, and installs the
  exact dependency versions from `uv.lock` into it.
* Adds the files from `deploy/`.
* Writes `dist/texas2step-<version>-<revision>-amd64.deb`, then runs lintian.
* Writes `dist/texas2step-setup`, the operators' setup tool, from
  `packaging/texas2step-setup.py`. It stamps in the package's file name and SHA-256, so
  the tool refuses any other package. Ship the two files together.

The virtualenv holds compiled wheels and links to the system Python, so build on the
Ubuntu release you're packaging for. The package then depends on that release's Python
minor version (3.14 for 26.04). For a packaging-only fix of the same version, use
`REVISION=2 make deb`.

To test an install without touching the build host, use a throwaway systemd container:

```bash
cat > Dockerfile.test <<'EOF'
FROM ubuntu:26.04
RUN apt-get update && DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends \
      systemd systemd-sysv dbus nginx curl ca-certificates python3 adduser
STOPSIGNAL SIGRTMIN+3
CMD ["/sbin/init"]
EOF
docker build -t t2s-test -f Dockerfile.test . && rm Dockerfile.test
docker run -d --name t2s-test --privileged --cgroupns=host \
    -v /sys/fs/cgroup:/sys/fs/cgroup:rw -p 127.0.0.1:18080:80 t2s-test
docker exec t2s-test rm -f /usr/sbin/policy-rc.d     # the image blocks service starts
docker cp dist/texas2step-*-amd64.deb t2s-test:/root/
docker exec t2s-test sh -c 'apt-get install -y /root/texas2step-*-amd64.deb'
```

Then add the include lines from [Install](install.md#2-publish-it-at-texas2step) to
`/etc/nginx/sites-available/default` in the container, reload nginx, and open
`http://127.0.0.1:18080/texas2step/`.

To test the setup tool instead, copy it in beside the package and use it in place of
`apt-get install`. The container's default site is plain HTTP, so name it:

```bash
docker cp dist/texas2step-setup t2s-test:/root/
docker exec -w /root t2s-test ./texas2step-setup --id austin \
    --site /etc/nginx/sites-enabled/default
docker exec -w /root t2s-test ./texas2step-install.sh
```

For an upgrade, install the previous release's `.deb` first and edit its settings, then
run the new setup tool. Add `ufw` to the image and enable it, after allowing 22 and 443,
to see the firewall step. `packaging/texas2step-setup.py` keeps its checks in pure
functions, which `tests/test_setup.py` covers with sample `nginx -T`, ufw, iptables and
nftables output.

## Release

1. Set the version in `src/texas2step/__init__.py`, the only place it is written. Everything
   else reads it from there:
   * `pyproject.toml`, through hatch's dynamic version, so the wheel and `pip show` too.
   * The server (`/api/v1/info`, `/api/v1/health`), and the web UI, which the server
     tells the version in each page it serves. No UI rebuild is needed for a new version.
   * The CLI (`texas2step --version`).
   * `packaging/build-deb.sh`, for the package version and file name.
   * `make version`, which prints it for scripts.

   The documentation doesn't repeat it.
2. If the release changes `src/texas2step/config_template.toml`, keep one setting per
   line, which is the layout `texas2step config merge` relies on. If it renames a
   setting, add the old and new names to `RENAMED` in `config_merge.py`, so upgrades
   carry the value across.
3. Run `make upgrade`, so the release ships every dependency's newest version, with its
   security and bug fixes.
4. Run `make check`, `make deb` and `make t2s`. The package installs exactly the
   versions in `uv.lock`, and t2s is built with exactly those in `t2s/go.sum`.
5. Commit (including the updated lockfiles), tag and publish the package:

```bash
v=$(make -s version)
git commit -am "Release $v" && git tag "v$v" && git push origin main "v$v"
gh release create "v$v" "dist/texas2step-$v-1-amd64.deb" dist/texas2step-setup \
    dist/t2s-linux-amd64 dist/t2s-linux-arm64 dist/t2s-macos-amd64 dist/t2s-macos-arm64 \
    dist/t2s-windows-amd64.exe dist/t2s-windows-arm64.exe \
    --title "texas2step $v" --generate-notes
```

6. Publishing the release publishes the Python package to
   [PyPI](https://pypi.org/project/texas2step/) too, for `uv tool install texas2step` and
   `pipx install texas2step`. `.github/workflows/pypi.yml` checks that the tag is
   `v<version>`, runs the tests, builds the sdist and wheel from the tag, checks their
   metadata, installs the wheel on its own and tests the server it starts. Then it uploads
   both files with PyPI's trusted publishing, with no API token. Watch it, then check the
   version's page on PyPI:

```bash
gh run watch "$(gh run list --workflow pypi.yml --limit 1 --json databaseId --jq '.[0].databaseId')" --exit-status
```

A version can be uploaded to PyPI only once. A run that fails before the upload can be
run again (`gh run rerun --failed <id>`). A fix that needs a new commit needs a new
version. To rehearse everything but the upload, run the workflow by hand: Actions →
pypi → Run workflow, or `gh workflow run pypi.yml`.

PyPI's copy of the README has its links made absolute, to GitHub, by
`hatch-fancy-pypi-readme` (`pyproject.toml`).

### Trusted publishing: the one-time setup

PyPI accepts the workflow's uploads because the project trusts it:

* On PyPI, under the project's **Settings → Publishing**, a GitHub trusted publisher
  with the repository's owner and name, the workflow `pypi.yml` and the environment
  `pypi`.
* On GitHub, under **Settings → Environments**, an environment named `pypi` whose
  deployments are limited to tags matching `v*`, so only a release tag can publish.

Without the workflow, a maintainer with a PyPI API token can still publish by hand:

```bash
uv build --out-dir build/pypi
UV_PUBLISH_TOKEN=<token> uv publish build/pypi/*
rm -rf build/pypi
```

`texas2step update` finds the two files on the release by their names
(`texas2step-<version>-<revision>-<arch>.deb` and `texas2step-setup`) and checks each
against the SHA-256 GitHub records for it, so attach them under exactly those names. It
runs the new release's setup tool with `--update`, so the setup tool must keep that
option and keep writing `texas2step-plan.json`.
